# v3 動量版本設計草案

## 背景

目前 Super Expert 主要透過放大地圖與增加地圖元素來提高複雜度。這會讓搜尋空間變大、路徑更長，但玩家體感上容易變成「更繁瑣」而不是「更困難又更好玩」。v3 應該把重點從單純擴張地圖，改成加入新的可推理互動規則，讓玩家可以利用機器人之間的碰撞產生更有趣的連鎖解法。

## 核心想法

加入簡化版「動量傳遞」概念：

1. A 機器人沿某方向滑行。
2. A 在滑行 `n` 格後撞到 B 機器人。
3. A 停在撞到 B 前的那一格，也就是現行規則中 A 原本會停下的位置。
4. B 獲得同方向的動量，並嘗試往同方向移動最多 `n` 格。
5. 如果 B 在移動過程中撞到牆壁，牆壁無條件吸收剩餘能量，連鎖立即結束。

這個版本的重點不是物理模擬，而是讓「移動距離」本身成為一種可以被規劃的資源。

## 建議規則定義

### 動量值

- 動量值等於主動移動機器人在撞擊前實際走過的格數。
- 如果 A 只走了 0 格，這不是有效移動，也不會產生動量。
- 若 A 沒有撞到其他機器人，而是撞到牆壁或邊界，行為維持現行規則：A 停在牆前一格。

### 撞擊機器人

- A 撞到 B 時，A 停在 B 前一格。
- B 會沿著 A 的移動方向最多移動 `n` 格。
- B 每前進一格消耗 1 點動量。
- B 不會主動轉向。
- 如果 A 一開始就緊貼 B，也就是 A 在撞到 B 前移動 0 格，這不是有效移動，B 不會被推動。

### 撞牆吸能

- B 推進途中如果下一格被牆壁、邊界、中央障礙、斜向牆等不可穿越阻擋，B 停在目前格子，剩餘動量歸零。
- 這條規則用來避免來回震盪，也讓牆壁成為明確的能量終點。

### 連鎖碰撞

v3 建議先採用「有限連鎖」：

- 如果 B 在帶有剩餘動量時撞到 C，B 停在 C 前一格。
- C 接收 B 剩餘的動量，繼續沿同方向移動。
- 每次穿越一格消耗 1 點動量。
- 任一機器人撞牆時，剩餘動量直接歸零。
- 例：A 走 3 格撞到 B；B 接收 3 格動量。若 B 走 1 格後撞到 C，C 接收剩下的 2 格動量。

這樣可以保留有趣的連鎖推理，又避免引入反彈、方向改變或能量保存造成的無限震盪。

### 步數計算

建議先維持「一次玩家指令算 1 步」：

- 玩家選擇一個機器人與方向，無論中間推動幾台機器人，都算 1 步。
- Solver 的狀態轉換也以一次指令作為一層 BFS/IDA 節點。

理由是玩家仍然只做了一次決策。若把每段被動移動也計入步數，規則會更難理解，也會削弱連鎖碰撞的獎勵感。

## 需要明確處理的邊界案例

1. A 旁邊就是 B：A 走 0 格時不推動 B，避免原地推擠變成另一套遊戲。
2. B 推進途中遇到另一台 C：觸發有限連鎖，而不是穿過或重疊。
3. B 推進途中遇到牆：B 停在牆前，剩餘動量消失。
4. B 的目標格被其他機器人佔據：視為碰撞，剩餘動量傳給該機器人。
5. 被動移動的機器人可以完成目標，因為這是 v3 連鎖解法的主要樂趣來源。
6. 斜向牆與 v2 Expert 元素：v3 prototype 先不加入斜向牆，等動量規則穩定後再評估。
7. Undo 必須記錄一次指令造成的所有機器人位置變化，而不是只記錄主動機器人。

## 對程式架構的影響

### GameEngine

目前 `move_robot(color, direction)` 只需要找出主動機器人的終點。v3 需要把移動拆成一個可以回傳完整結果的規則函式：

- 輸入：目前機器人位置、主動機器人、方向、地圖。
- 輸出：新機器人位置、是否有效移動、碰撞/推動事件列表。

建議新增純邏輯函式，例如：

```python
resolve_momentum_move(board, robots, color, direction, grid_size, diagonal_walls=None)
```

GUI、solver、測試都共用同一個函式，避免遊戲與解題器規則分歧。

### Solver

Solver 的狀態轉換要從「單一機器人滑到終點」改成「一次指令可能更新多台機器人」。狀態仍然可以維持目前 tuple of positions 的表示法，只是產生下一狀態的 transition 函式會更複雜。

由於動量會增加分支結果的差異，建議 v3 solver 一開始先保守設定：

- 16x16 地圖優先。
- 先關閉 diagonal walls。
- 保留 `max_depth` 與 `max_states` 限制。
- 加入規則層的單元測試，再調整搜尋性能。

### GUI

GUI 需要能呈現一次移動中多台機器人被推動。v3 第一版可以先不做完整逐格動畫，只要最終位置正確、move history 可 undo 即可。之後再補事件列表動畫。

## 建議實作階段

### Phase 1：規則原型

- 新增 `momentum_rules.py` 或在 `game_engine.py` 中先做純函式。
- 加入單元測試覆蓋直線推動、撞牆吸能、連鎖碰撞、0 格不推動。
- 暫時只支援 16x16、無 diagonal walls。

### Phase 2：接入遊戲

- 在 `GameEngine` 加入 v3 difficulty/mode。
- `move_history` 改成記錄一次移動前的完整 robots dict。
- GUI 可切換 v3 模式並正確 undo。

### Phase 3：接入 solver

- Solver 狀態轉換改用共用規則函式。
- 加入小型固定地圖測試，確認最短步數符合預期。
- 評估是否需要 IDA* 或更強的 heuristic。

### Phase 4：關卡設計

- 暫停以「更大地圖」作為主要難度來源。
- 使用 16x16 或略大地圖，設計需要距離控制與連鎖推動的題目。
- 以玩家可看懂的動量路徑作為核心樂趣。

## 開放問題

1. 被動推動的機器人能否完成目標？建議可以，因為這會鼓勵更有趣的解法。
2. Silver robot 是否參與動量？建議先視為一般機器人。
3. diagonal walls 是否能改變被推動機器人的方向？建議 v3 初版先禁用，避免規則過早膨脹。
4. 動量值是否要有上限？建議先不設上限，因為地圖大小已自然限制最大值。
5. 玩家介面是否要顯示推動距離？建議等規則穩定後再做，可用短暫數字或軌跡提示。
